## 핵심 개념: 공개 모드

지금처럼 내 컴퓨터에서 `python3`·`php -S`로 켜는 방식(**개발 모드**)은 그대로 둔다(헌법 II). 운영자가 **공개 모드**를
켰을 때만 아래의 엄격한 규칙(HTTPS 전제, Secure 쿠키, 기본 비밀번호 거부, 공개 주소 필수)이 적용된다.
공개 모드는 두 서버가 같은 값을 보도록 한 곳의 설정으로 켠다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 기본 관리자 비밀번호로는 공개 서버가 켜지지 않는다 (Priority: P1)

운영자가 공개 모드로 블로그를 켤 때, 관리자 비밀번호를 정하지 않았거나 알려진 기본값(admin1234)·너무 약한 값이면
서버가 켜지지 않고 무엇을 해야 하는지 한국어로 안내한다. 지금은 BLOG_PASSWORD 없이 켜면 조용히 admin1234로 돌아가,
누구나 관리자로 로그인해 모든 글·회원을 지울 수 있다.

**Why this priority**: 공개 직후 가장 먼저 노려지는 구멍이고, 뚫리면 데이터 전체(헌법 IV)를 잃는다. 다른 스토리 없이도
단독으로 의미가 있다.

**Independent Test**: 공개 모드로 비밀번호 없이·admin1234로·짧은 값으로 각각 켜 보고 모두 거절되는지, 강한 비밀번호로는
켜지고 그 비밀번호로만 admin 로그인이 되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 공개 모드이고 관리자 비밀번호를 정하지 않았으면, **When** 블로그 서버를 켜면, **Then** 켜지지 않고
   "공개 모드에서는 관리자 비밀번호를 정해야 해요"와 정하는 방법을 보여 준다. DB는 건드리지 않는다.
2. **Given** 공개 모드이고 비밀번호가 admin1234이거나 규칙(12자 이상, 영문+숫자)에 못 미치면, **Then** 같은 방식으로 거절한다.
3. **Given** 공개 모드이고 규칙에 맞는 비밀번호를 정했으면, **Then** 서버가 켜지고 admin은 그 비밀번호로만 로그인된다.
   예전 비밀번호(admin1234 포함)로는 로그인되지 않는다.
4. **Given** 관리자 비밀번호를 바꿔 다시 켜면, **Then** 기존 관리자 로그인(2주 세션)은 모두 끊긴다.
5. **Given** 개발 모드이면, **Then** 지금처럼 기본값으로도 켜지고 켤 때 바꾸라는 안내만 나온다(NFR-09 유지).

### User Story 2 - 공개 주소와 HTTPS로 안전하게 접속한다 (Priority: P1)

운영자는 블로그·회원 서버의 공개 주소(예: https://blog.example.com, https://auth.example.com)를 설정 한 곳에 넣으면,
입장권·로그아웃 표·서버 간 요청·SNS 로그인 돌아오는 주소가 모두 그 주소를 쓴다. 방문자는 항상 HTTPS로 접속하고,
로그인 쿠키는 HTTPS에서만 전송된다. 회원 서버는 개발용 내장 서버가 아니라 정식 웹 서버에서 공개 폴더(public/)만
바깥에 보이게 돈다.

**Why this priority**: HTTPS 없이 공개하면 비밀번호·세션이 그대로 노출된다. 주소 설정이 없으면 공개 자체가 안 된다.

**Independent Test**: 공개 주소를 넣고 공개 모드로 켠 뒤, http로 접속하면 https로 옮겨지는지, 로그인 쿠키에 Secure가
붙는지, 회원 가입 → 블로그 입장 → 로그아웃(두 서버 함께)이 공개 주소로 끝까지 되는지, 회원 서버의 DB·키 파일이
주소로 열리지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 공개 모드이고, **When** 누군가 http 주소로 들어오면, **Then** 같은 경로의 https 주소로 옮겨진다.
2. **Given** 공개 모드에서 로그인하면, **Then** 블로그·회원 서버 세션 쿠키 모두 HttpOnly·Secure를 갖고, 기존 SameSite 규칙(SEC-05)을 유지한다.
3. **Given** 공개 주소가 설정돼 있으면, **When** 회원 서버에서 블로그로 들어가거나 블로그에서 로그아웃하면, **Then** 입장권·로그아웃 표가 설정된 공개 주소로만 오가고, 다른 주소로 돌려보내지 않는다(SEC-07 유지).
4. **Given** SNS 로그인 키가 등록돼 있으면, **Then** SNS 돌아오는 주소(Callback)는 설정된 회원 서버 공개 주소로 만들어지고, 운영자는 관리 화면이나 시작 안내에서 각 SNS 개발자 콘솔에 넣을 정확한 주소를 볼 수 있다.
5. **Given** 공개 모드인데 공개 주소가 비었거나 https가 아니면, **Then** 서버가 켜지지 않고 무엇을 넣어야 하는지 안내한다.
6. **Given** 회원 서버가 정식 웹 서버에서 돌 때, **When** 누군가 db/·sso.key·oauth.config.php 등 공개 폴더 밖 파일을 주소로 요청하면, **Then** 열리지 않는다(SEC-10).
7. **Given** 개발 모드이면, **Then** 지금처럼 http://localhost 주소로 동작한다.

### User Story 3 - 프록시 뒤에서도 로그인 잠금이 사람마다 걸린다 (Priority: P2)

공개 서버는 보통 HTTPS를 맡는 앞단(리버스 프록시) 뒤에서 돈다. 이때 서버가 보는 접속 IP가 모두 프록시 하나로 보이면,
"같은 IP로 15분 5번" 잠금(SEC-03)이 한 사람 때문에 모두를 막거나, 반대로 아무도 막지 못한다. 운영자가 믿는 프록시를
지정하면 서버는 실제 방문자 IP를 기준으로 잠금·횟수 제한을 건다.

**Why this priority**: US2를 하면 바로 생기는 부작용이라 P1 다음이다. 단독으로도 확인할 수 있다.

**Independent Test**: 믿는 프록시를 지정한 상태에서 서로 다른 두 방문자 IP로 로그인 실패를 내면 각각 따로 세어지는지,
믿지 않는 곳에서 보낸 가짜 IP 머리글은 무시되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 믿는 프록시가 지정돼 있고, **When** 프록시를 거쳐 들어온 요청이면, **Then** 프록시가 알려 준 실제 방문자 IP로 잠금·횟수 제한을 센다.
2. **Given** 믿는 프록시가 아닌 곳에서 IP 머리글을 붙여 보내면, **Then** 그 머리글은 무시하고 실제 접속 IP를 쓴다.
3. **Given** 믿는 프록시가 지정되지 않았으면, **Then** 지금처럼 접속 IP를 쓴다.

### User Story 4 - 자동·대량 가입을 막는다 (Priority: P2)

공개하면 프로그램이 가입을 대량으로 보내 스팸 블로그를 만든다. 지금은 아이디 중복 확인(세션당 5분 30번) 말고는 가입
횟수 제한이 없다. 앞으로는 같은 곳에서 짧은 시간에 여러 번 가입할 수 없고, 사람이 아닌 자동 가입을 걸러 낸다.
정상 사용자의 가입 과정은 지금보다 크게 길어지지 않는다.

**Why this priority**: 스팸은 피해가 크지만 데이터 유출·탈취는 아니고, '회원가입 허용' 끄기(AUTH-14)로 급한 대응은 이미 된다.

**Independent Test**: 같은 IP에서 정해진 횟수를 넘겨 가입하면 거절되는지, 자동 가입 방지 확인을 거치지 않은 가입
요청(화면을 우회한 직접 요청 포함)이 거절되는지, 정상 사용자는 한 번에 가입되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 같은 방문자 IP에서 1시간 안에 3개 계정을 만들었으면, **When** 4번째 가입(일반·SNS 첫 가입 모두)을 하면, **Then** "잠시 뒤 다시 시도해 주세요"로 거절된다. 서버를 다시 켜도 횟수는 유지된다.
2. **Given** 사이트 전체에서 1시간 안에 새 가입이 30개를 넘으면, **Then** 이후 가입은 잠시 막히고, 관리자 화면에 이 사실이 표시된다.
3. **Given** 가입 요청이 자동 가입 방지 확인을 통과하지 못했으면(화면을 우회한 직접 요청 포함), **Then** 서버가 거절한다(헌법 I).
4. **Given** 사람이 보통 속도로 가입 화면을 채워 보내면, **Then** 추가로 입력할 것 없이 지금과 같이 한 번에 가입된다.
5. **Given** 개발 모드이면, **Then** 횟수 제한은 동작하되 자동 가입 방지 확인은 켜고 끌 수 있다.

### Edge Cases

- 공개 모드에서 관리자 비밀번호를 잊으면? → 운영자가 서버 설정에서 새 비밀번호를 넣고 다시 켜면 된다(서버를 켤 수 있는 사람만 가능).
- 블로그와 회원 서버의 공개 모드·공개 주소 설정이 서로 다르면? → 두 서버가 같은 설정 파일 하나를 읽으므로 원칙적으로 다를 수 없다. 블로그 실행 환경에 남은 주소 환경변수가 파일 값과 다르면 공개 모드에서는 블로그가 켜지지 않고 안내한다. 서버 간 서명 요청은 기존처럼 sso.key로만 신뢰한다(헌법 III).
- 공개 주소를 바꾸면 이미 발급된 입장권·로그아웃 표는? → 만료(5분·1분)까지 기다리면 되고, 블로그 로그인(2주)은 유지된다.
- 공개 주소를 바꾼 뒤 SNS 개발자 콘솔의 Callback을 안 바꾸면? → SNS 쪽이 오류 화면을 보여 로그인이 안 된다(우리 화면으로 돌아오지 않음). 돌아온 뒤 실패하면 지금처럼 "SNS 로그인 중 문제가 생겼어요"로 안내한다. 운영자는 관리 화면의 콜백 주소와 SNS 콘솔 등록 값을 비교해 고친다(키·비밀값은 노출하지 않음).
- 같은 와이파이 공유(HOST=0.0.0.0, NFR-12)처럼 https 없이 다른 기기에서 쓰려면? → 개발 모드로 취급한다. 공개 모드와 섞지 않는다.
- 가입 횟수 제한에 걸린 공유 IP(학교·회사)는? → 1시간 뒤 풀리고, 관리자는 '회원가입 허용'으로 전체만 조절한다. IP별 예외 목록은 범위 밖.
- 관리자 비밀번호를 강하게 바꿨는데 예전 admin1234 해시가 DB에 남아 있으면? → 켤 때 설정값 기준으로 해시를 다시 저장해 예전 비밀번호는 무효가 된다.

## Clarifications

### Session 2026-10-08

- Q: 자동 가입 방지 방식은? → A: 외부 서비스 없는 자체 방식(숨은 칸 + 최소 작성 시간 + 서버 발급 1회용 값)
- Q: 안내·설정 예시의 배포 대상 환경은? → A: 리눅스 VPS(Ubuntu) + Nginx(HTTPS, Let's Encrypt) + PHP-FPM, 블로그 서버는 Nginx 뒤

### 계획(plan) 중 정한 것 2026-10-08

- 공개 설정은 두 서버가 함께 읽는 파일 하나(deploy.config.json, 웹 폴더 밖)에 두고, 관리자 비밀번호는 넣지 않는다(research R1·R2).
- 공개 주소는 https 오리진만(경로 없음), 블로그·회원 서버는 서로 다른 호스트(R7).
- 공개 모드의 회원 서버는 php -S 실행을 거절한다. 로컬 점검용 예외 하나만 둔다(R8).
- 가입 현황에는 IP를 보이지 않는다. 대신 SNS 콜백 주소와 키가 등록된 SNS 목록을 함께 보인다(R12).

## Requirements *(mandatory)*

### Functional Requirements

**공개 모드 공통**

- **FR-001**: 두 서버는 MUST 한 곳의 설정으로 공개 모드를 켜고 끌 수 있고, 꺼져 있으면 지금 동작(개발 모드)을 그대로 유지한다. (NFR-07, NFR-12, 새 NFR-13)
- **FR-002**: 공개 모드에서 필수 설정(관리자 비밀번호, 두 서버의 https 공개 주소)이 빠지거나 틀리면 MUST 서버가 켜지지 않고, 빠진 항목과 넣는 방법을 한국어로 안내한다. DB·파일은 건드리지 않는다. (NFR-09, 헌법 IV·VI)

**관리자 비밀번호 (US1)**

- **FR-003**: 공개 모드에서는 MUST 관리자 비밀번호가 없거나 알려진 기본값이거나 12자 미만·영문+숫자 미포함이면 서버를 켜지 않는다. (새 SEC-15)
- **FR-004**: 관리자 비밀번호를 바꾸고 켜면 MUST 예전 비밀번호로는 로그인되지 않고 기존 관리자 세션이 모두 끊긴다. 저장은 기존 해시 규칙(SEC-02)을 따른다.

**HTTPS·쿠키·주소 (US2)**

- **FR-005**: 공개 모드에서 http 요청은 MUST https로 옮겨지고, 브라우저가 이후에도 https만 쓰도록 알린다. (새 SEC-13)
- **FR-006**: 공개 모드에서 두 서버의 세션 쿠키는 MUST Secure를 갖고, 기존 HttpOnly·SameSite 규칙을 유지한다. (SEC-05, SEC-06, 새 SEC-13)
- **FR-007**: 입장권·로그아웃 표·서버 간 요청·돌려보내기 주소·SNS Callback 주소는 MUST 설정된 공개 주소에서 만들어지며, 요청에 실려 온 Host 값으로 주소를 만들지 않는다. (SEC-07, SEC-08, AUTH-06, 새 NFR-13)
- **FR-008**: 운영자는 MUST 각 SNS 개발자 콘솔에 등록할 Callback 주소를 확인할 수 있다(키·비밀값은 보이지 않음). (SEC-10)
- **FR-009**: 공개 운영 시 회원 서버는 MUST 정식 웹 서버에서 공개 폴더(public/)만 바깥에 보이게 실행할 수 있고, 그 설정 예시와 확인 절차가 제공된다. 공개 폴더 밖 파일은 주소로 열리지 않는다. 공개 모드에서 개발용 내장 서버(php -S)로 켜면 MUST 요청을 거절하고 정식 웹 서버로 실행하라고 안내한다(로컬 점검용 예외만 허용). (SEC-10, 새 NFR-14)
- **FR-010**: 블로그 서버의 공개 운영 방법(HTTPS를 맡는 앞단 뒤에서 실행)도 MUST 같은 문서에 설정 예시와 확인 절차로 제공된다. (새 NFR-14)

**실제 방문자 IP (US3)**

- **FR-011**: 운영자가 믿는 프록시를 지정하면 MUST 두 서버의 모든 IP 기준 제한(로그인 잠금, 댓글 비밀번호 잠금, 가입 횟수 등)이 프록시가 알려 준 실제 방문자 IP를 쓰고, 믿지 않는 곳에서 온 IP 머리글은 무시한다. (SEC-03, 새 SEC-16)

**가입 남용 방지 (US4)**

- **FR-012**: 회원 서버는 MUST 같은 방문자 IP에서 1시간 안에 3개를 넘는 가입(일반·SNS 첫 가입 합산)과 사이트 전체 1시간 30개를 넘는 가입을 거절하고, 이 기록은 서버를 다시 켜도 유지된다. (AUTH-01, AUTH-06, 새 SEC-14)
- **FR-013**: 회원 서버는 MUST 자동 가입 방지 확인을 통과한 가입만 받고, 이 검사는 서버에서 한다. 확인은 외부 서비스 없이 자체 방식으로 한다: 사람에게 보이지 않는 칸이 채워졌거나, 가입 화면을 연 뒤 너무 빨리(3초 미만) 보냈거나, 서버가 화면을 열 때 발급한 1회용 값이 없거나 이미 쓰였거나 만료(30분)됐으면 거절한다. 사용자에게 추가 입력을 요구하지 않는다. (새 SEC-14, 헌법 I·II)
- **FR-014**: 관리자 사이트 설정 화면에 MUST 최근 24시간 가입 현황(성공 수, 이유별 막힌 수, 지금 사이트 전체 제한이 걸렸는지)이 보인다. 방문자 IP는 보여 주지 않는다. (새 SEC-14, AUTH-14)

**공통**

- **FR-015**: 새 화면·문구·안내는 MUST 한국어, 회원·블로그 디자인 규칙(NFR-01·NFR-04)과 접근성(NFR-10)을 따른다.
- **FR-016**: 구현 후 MUST requirements.md와 원본 문서에 새 ID(SEC-13~16, NFR-13~14)를 추가하고 7장 '인터넷 공개(배포)와 HTTPS' 과제를 갱신한다. (헌법 V)

### Key Entities

- **공개 설정(배포 설정 파일 `deploy.config.json`)**: 공개 모드 여부, 블로그·회원 서버 공개 주소, 믿는 프록시 목록, 가입 제한 값. 두 서버가 같은 파일을 읽고, 파일은 웹 폴더 밖에 둔다. 관리자 비밀번호 같은 비밀값은 이 파일에 넣지 않고 블로그 서버 실행 환경에만 둔다.
- **가입 기록**: 가입 시각과 방문자 IP(잠금 판단용, 일정 기간 뒤 정리). 회원 계정과 별개로 남는다.
- **자동 가입 방지 확인 값**: 가입 화면을 열 때 서버가 발급하고, 가입 때 서버가 확인하는 1회용 값.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 공개 모드에서 기본·약한 관리자 비밀번호로 서버가 켜지는 경우가 0건이고, admin1234로 관리자 로그인이 되는 경우가 0건이다.
- **SC-002**: 공개 모드에서 비밀번호·세션 쿠키가 암호화되지 않은 연결로 오가는 요청이 0건이다(http로 들어온 요청은 모두 https로 옮겨짐).
- **SC-003**: 운영자가 이 기능의 안내 문서만 보고 빈 서버에 두 서버를 공개 주소로 띄워 가입 → 블로그 입장 → 글쓰기 → 함께 로그아웃까지 1시간 안에 마칠 수 있다.
- **SC-004**: 회원 서버 공개 주소로 DB·키·SNS 설정 파일을 요청해 내용이 보이는 경우가 0건이다.
- **SC-005**: 자동화 도구로 1시간 동안 가입을 시도해도 같은 IP에서 만들어지는 계정이 3개 이하이고, 화면을 거치지 않은 직접 가입 요청으로 만들어지는 계정은 0개다.
- **SC-006**: 정상 사용자의 가입 완료 시간이 지금보다 30초 이상 늘지 않는다.
- **SC-007**: 개발 모드에서 기존 실행 방법(`python3`, `php -S`)과 기존 blog.db·회원 DB가 그대로 동작한다.

## Assumptions

- 실제 서버 구매·도메인 등록·DNS 설정·인증서 발급은 운영자가 하며, 이 기능은 그 위에서 앱이 안전하게 돌도록 준비하고 방법을 안내한다. 실제 배포 실행은 범위 밖. 안내 문서와 설정 예시는 리눅스 VPS(Ubuntu) + Nginx(HTTPS, Let's Encrypt 인증서) + PHP-FPM, 블로그 서버는 Nginx 뒤에서 상시 실행되는 구성을 기준으로 한다.
- HTTPS 암호화는 앞단 웹 서버(또는 호스팅)가 맡고, 블로그 서버(Python 표준 라이브러리)가 직접 인증서를 다루지 않는다.
- 두 서버는 같은 기계 또는 서로 직접 부를 수 있는 곳에서 돌며, 서로 다른 하위 도메인(예: blog.내도메인, auth.내도메인)을 쓴다. 같은 도메인의 다른 경로로 나누는 구성은 지원하지 않는다.
- 관리자 비밀번호 규칙(12자 이상, 영문+숫자)은 회원 규칙(8자)보다 강하게 둔다. 관리자 2단계 인증은 범위 밖.
- 가입 횟수 기준(IP당 1시간 3개, 전체 1시간 30개)은 개인 블로그 규모 기준의 기본값이며 설정으로 바꿀 수 있다.
- 백업 자동화·CDN 끊김 대비·이메일 인증은 이 기능의 범위 밖이다(다른 과제).
- 자동 가입 방지는 자체 방식이라 새 외부 의존성이 없다(헌법 II 유지). 사람처럼 동작하는 정교한 봇은 일부 통과할 수 있으며, 그 경우 가입 횟수 제한과 '회원가입 허용' 끄기가 2차 방어다.
