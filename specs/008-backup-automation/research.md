# Research: 백업 자동화

**Date**: 2026-10-08 | **Spec**: [spec.md](./spec.md)

## 결정

### D1. DB는 SQLite 온라인 백업

- **Decision**: `sqlite3.connect(<경로 URI>?mode=rw, uri=True).backup(dst)` 후 `PRAGMA integrity_check`가 `ok`일 때만 완성.
- **Rationale**: 회원 DB는 `journal_mode = WAL`이라 파일만 복사하면 `-wal`에 있는 최근 변경이 빠지거나 반쯤 쓴 상태가 복사될 수 있다. 온라인 백업은
  서버가 쓰는 중에도 한 시점의 온전한 사본을 만든다. `mode=rw`는 없는 DB를 새로 만들지 않게 한다.
- **Alternatives**: 서버를 멈추고 tar(지금 deploy/README 방식) → 자동화가 어렵고 멈춤이 생김. `VACUUM INTO` → SQLite 3.27 이상, 쓰는 중 잠금이 김.

### D2. 업로드는 하드 링크로 이어 쌓기

- **Decision**: 앞 백업의 manifest에 같은 경로·크기가 있고 원본 수정 시각이 앞 백업 시각보다 이전이면 `os.link`(실패하면 복사), 확인값은 앞 manifest 값을
  다시 씀. 새 파일만 복사·해시.
- **Rationale**: 업로드는 이름이 무작위이고 한 번 올리면 바뀌지 않는다(지울 때만 사라짐). 매일 백업 14개를 그대로 복사하면 사진 용량이 14배가 된다.
- **Alternatives**: 날마다 전체 복사 → 용량. rsync → 설치 필요(헌법 II).

### D3. 자동 백업은 켜는 스크립트가 맡는다

- **Decision**: `start-blog.command`가 켜기 전에 `--daily`, 켜져 있는 동안 1시간마다 `--daily`(백그라운드 반복, 끌 때 함께 종료). VPS는 systemd 타이머.
- **Rationale**: server.py를 백업 코드와 묶지 않는다(서버는 웹만). 맥에서 며칠 켜 두어도 날짜가 바뀌면 백업된다.
- **Alternatives**: server.py 안 스레드 → 서버 사용자에게 백업 폴더 쓰기 권한·코드 결합. launchd → 사용자가 설정 파일을 등록해야 함.

### D4. 정리 규칙

- **Decision**: `--keep 14`(0이면 정리 안 함). 대상은 백업 위치 바로 아래 `^\d{4}-\d{2}-\d{2}_\d{6}(-\d+)?$` 폴더 중 `manifest.json`이 있는 것만.
  `_before-restore`·다른 이름·임시 폴더는 대상 아님(임시 폴더는 하루 지난 것만 지움).
- **Rationale**: 사람이 넣은 폴더나 안전 백업을 실수로 지우지 않음.

### D5. 복원은 "백업 그대로"

- **Decision**: 확인값 전부 검사 → 서버 포트(기본 8000·8080, `PORT` 환경변수 반영)에 연결되면 거절 → 안전 백업 → 각 파일을 대상 폴더의 임시 이름에 쓴 뒤
  `os.replace` → 두 DB의 낡은 `-wal`·`-shm` 삭제 → uploads는 백업에 없는 파일 삭제 → 백업에 없던 선택 파일(oauth·설정)도 치움(안전 백업에 남음).
- **Rationale**: 일부만 되돌리면 회원 번호·서명 키가 어긋난다(7장 남은 과제의 위험). 낡은 WAL이 남으면 SQLite가 새 DB에 옛 변경을 덧씌워 손상될 수 있다.
- **Alternatives**: 블로그 화면에서 복원 → 서버를 꺼야 해서 불가, 비밀 파일을 화면으로 다루게 됨.

### D6. 권한과 잠금

- **Decision**: 백업 위치·백업 폴더 700, DB·sso.key·oauth.config.php·deploy.config.json·manifest 600, 업로드는 원래 권한. 잠금은 백업 위치의 `.lock`에
  `fcntl.flock`(비차단), 이미 잠겨 있으면 "다른 백업이 진행 중이에요".

### D7. 독립 검토에서 찾은 문제와 해결 (구현 후 검토, 2026-10-08)

| 심각도 | 문제 | 해결 |
| --- | --- | --- |
| 높음 | blog.db가 없으면 안전 백업을 건너뛰어 회원 DB·키·업로드가 복사본 없이 바뀜 | 안전 백업은 있는 것을 모두 남김(blog.db 없어도) |
| 중간 | 지금 DB가 망가져 있으면(되돌릴 가장 흔한 이유) 안전 백업의 무결성 검사에 걸려 복원 자체가 안 됨 | 안전 백업에서만 파일째 복사(+ `-wal`·`-shm`·`-journal`), `raw_copies`에 기록 |
| 중간 | 파일을 하나씩 바꾸다 중간에 실패하면 블로그 DB는 백업 것, 회원 DB는 지금 것으로 엇갈림 | 1단계 준비(임시 파일) → 2단계 한꺼번에 이름 바꾸기, 실패하면 안전 백업으로 자동 되돌림 |
| 중간 | root로 한 번 백업하면 그 뒤 블로그 사용자의 백업·목록이 권한 오류로 계속 실패, 정리 실패를 백업 실패로 보고 | 백업도 root 실행을 막음, 목록은 읽을 수 없는 항목을 건너뜀, 정리 실패는 경고 |
| 중하 | 백업에 설정 파일이 없으면 복원이 지워 공개 서버가 개발 모드로 돌아갈 수 있음(맥 백업을 서버에 복원 등) | 설정 파일은 기본으로 이 컴퓨터 것을 그대로, `--with-config`일 때만 백업 그대로 |
| 중하 | 맥의 `php -S localhost`는 ::1에 열릴 수 있어 127.0.0.1만 보면 켜진 회원 서버를 놓침, 공개 운영의 PHP-FPM은 소켓 | localhost가 가리키는 모든 주소 + PHP-FPM 소켓 확인 |
| 낮음 | 복원이 잠금을 잡지 않아 자동 백업이 끼어들 수 있음 | 복원하는 동안 백업 위치 잠금 |
| 낮음 | 하드 링크된 업로드 하나가 손상되면 모든 백업이 복원 거절, 다음 백업도 손상 파일을 이음 | 업로드 손상은 그 파일만 빼고 되돌림, 링크 전에 앞 백업 파일의 확인값도 검사 |
| 낮음 | 이미 있는 폴더(예: /tmp)를 백업 위치로 주면 권한을 700으로 바꿈, 남이 쓰는 폴더의 `.lock` 링크를 따라감 | 만든 폴더만 700, 남도 쓰는 폴더·남의 폴더는 거절, `.lock`은 링크를 따라가지 않음, 남의 백업은 복원 거절 |
| 낮음 | 복원 임시 파일이 잠깐 644·이름이 정해져 있음 | 처음부터 600·무작위 숨은 이름·실패하면 지움 |
| 낮음(문서) | 서버 백업을 내 컴퓨터로 옮기는 `rsync -a`가 권한 때문에 실패하고 하드 링크를 풀어 용량이 늘어남 | `rsync -aH --rsync-path="sudo rsync"` |

그 밖에 Ctrl + C 때 한국어 안내, systemd 백업은 `--kind auto`, 업로드 이름 검사는 `fullmatch`로 바꿨다.
